SB 153 Compliance
Built for California AR Rules
  • 10-day cap: System enforces max 10 AR credits per student per year (or total absences if fewer)
  • 1-hour increments: ADA generated in hourly units per SB 153
  • Grade-aligned content: Session content tagging to verify standards alignment
  • Session types: Before/after school, weekends, intersession, summer recess
  • CALPADS STAS export: Generates compliant Student Absence Summary file for EOY 3 submission
Revenue Calculation Engine
Real-Time ADA Delta Math
  • Per-district LCFF rate: Configurable base grant per ADA by grade span (K-3, 4-6, 7-8, 9-12)
  • ADA delta formula: (recovered_hours / instructional_day_minutes) x daily_rate
  • Reporting periods: Tracks against P1, P2, Annual certification deadlines
  • Revenue dashboard: Real-time recovered vs. projected revenue by school, grade, session type
  • Audit packet: Generates compliance documentation for district CFO/CBO review

Data Pipeline Architecture

Batch-First Sync Strategy
  • Why batch-first: Districts rarely grant real-time API access. CSV and nightly batch are the realistic starting point for 90%+ of districts
  • Sync cadence: Nightly for attendance data (via BullMQ scheduled jobs), on-demand for demographic updates
  • Conflict resolution: SIS is source of truth for demographics; platform is source of truth for AR session data
  • Data quality gate: Every import runs through validation before commit. Bad rows surface for operator review, never silently fail
Standards Support
  • OneRoster 1.1: REST + CSV rostering standard for student/class/enrollment data. Supported by Aeries, PowerSchool, Infinite Campus
  • Ed-Fi: Comprehensive data standard. District adoption growing but uneven. Support planned for v1.0+
  • CALPADS: California-specific. Platform must generate STAS (Student Absence Summary) files for AR reporting
  • Middleware option: Edlink or Clever as abstraction layer evaluated; custom connectors preferred for attendance-depth data
Security Architecture

FERPA + HIPAA + SOC 2 from Day One

Compliance is architectural, not a checklist bolted on later. The regulatory stack determines data model decisions, hosting choices, and access patterns.

Module 1 -- FERPA
Student Education Records
  • FERPA applies to all student attendance, demographic, and academic data
  • Requires written parent consent for data sharing outside "school official" exception
  • CA-NDPA (National Data Privacy Agreement) required before first district contract
  • Student Privacy Pledge v2.0 signatory recommended
  • No PII in logs, URLs, or error reports
  • Data minimization: collect only what's needed for ADA recovery
Module 2 -- HIPAA
Protected Health Information
  • HIPAA triggered by mental health service records, clinical notes, and billing data
  • Business Associate Agreement (BAA) with every district required
  • PHI must be encrypted at rest (AES-256) and in transit (TLS 1.2+)
  • Access logs with 6-year retention
  • Breach notification within 60 days
  • Architectural isolation: MH data stored in separate schema with stricter RLS policies
Infrastructure
SOC 2 Type 2 + CA-Specific
  • SOC 2 Type 2 audit within 12 months of launch (required by most district procurement)
  • SOPIPA (Student Online Personal Information Protection Act) -- CA state law, stricter than COPPA
  • CMIA (Confidentiality of Medical Information Act) -- CA medical data law, applies to MH records
  • PostgreSQL RLS enforces tenant isolation at the database level
  • All infrastructure on US-based cloud (AWS us-west-2 or GCP us-west1)

Technology Decisions

Tech Stack Rationale

Every technology choice optimizes for three things: speed to v0.1, compliance readiness, and the ability to add Module 2 without rewriting.

Backend
NestJS (TypeScript)
  • Why NestJS: Module system maps directly to EduFund's module architecture (ADA module, MH module, SIS module). Each NestJS module encapsulates its own controllers, services, and Prisma repositories
  • Why not Express: No structure. EduFund needs guards (RBAC), interceptors (audit logging), and pipes (Zod validation) at the framework level
  • Why not Next.js API routes: Pre-flight decision excluded SSR. Separating frontend from API allows independent scaling and cleaner compliance boundary
  • Middleware stack: Helmet (security headers), compression, CORS (district-whitelisted origins), rate limiting (per-tenant)
Frontend
React SPA + Tailwind CSS
  • Why React SPA: Dashboard-heavy app with complex state (multi-district, multi-school drill-down). SPA delivers snappy navigation for operators managing 17+ districts
  • State management: Zustand for client state. React Query for server cache with optimistic updates
  • Component library: Headless UI + Tailwind. No heavy component library -- keeps bundle lean for mobile/PWA
  • Charts: Recharts for revenue dashboards. Lightweight, React-native, good enough for v0.1
  • PWA: Service worker for offline attendance capture at school sites with spotty connectivity
Database
PostgreSQL + Prisma + RLS
  • Why PostgreSQL: Row Level Security for tenant isolation. JSONB for flexible district settings. Mature, proven at scale in ed-tech (PowerSchool, Clever, Panorama all use Postgres)
  • Why Prisma: Type-safe database access, migration system, introspection. Zod integration via prisma-zod-generator for shared validation
  • Why not Supabase: Direct Postgres with RLS gives the same security model without platform lock-in. Compliance auditors prefer infrastructure you control
  • Hosting: AWS RDS (Multi-AZ) or Neon for serverless Postgres. Automated backups with point-in-time recovery
Infrastructure
BullMQ + Redis + S3
  • BullMQ: Background job processing for SIS sync, CSV import validation, report generation, notification dispatch. Redis-backed with retry policies and dead-letter queues
  • Redis: Job queue backing store + session cache + rate limit counters. Not used for primary data storage
  • S3: CSV upload staging, generated PDF reports, audit log archives. Server-side encryption (AES-256)
  • Deployment: Docker containers on AWS ECS Fargate (or Railway/Render for v0.1 simplicity). CI/CD via GitHub Actions

Business Model

Two Scenarios: High-Touch vs. Low-Touch

Per pre-flight decision, both scenarios are modeled pending real district revenue data from Phase 1 pilot. Final model selected after 3-district validation.

Scenario A: Platform SaaS
Low-Touch, Predictable Revenue
  • Pricing: $500/active district/month ($5,400/yr with annual prepay)
  • Setup fee: $8,500 one-time (covers onboarding, data migration, training)
  • Revenue at 17 districts: $8,500/month = $102K/year recurring
  • Revenue at 50 districts: $25,000/month = $300K/year recurring
  • Gross margin: ~80% at scale (infrastructure costs ~$100/district/month)

Best for: Predictable cash flow, easier to sell, districts understand subscription models. Matches the Bizpleaser.ai Option B pricing already proposed to AARC.

Scenario B: Revenue Share
High-Touch, Aligned Incentives
  • Pricing: 7% of incremental ADA recovery revenue, paid quarterly
  • Setup fee: $5,000 (reduced, offset by ongoing share)
  • Revenue per district: If a district recovers $500K/year, platform earns $35K/year
  • Revenue at 17 districts: $595K/year (at $500K avg recovery)
  • Cap: $200K total per district over 4-year term

Best for: Higher revenue per district, aligned to AARC's growth, supports acquisition narrative. Matches Bizpleaser.ai Option C.

Districts Billing Under CYBHI
  • SB 153 (July 2025): Formalizes attendance recovery programs statewide. Creates greenfield demand for compliant software. Districts can now generate ADA in 1-hour increments across Saturday, before/after school, intersession, and summer sessions
  • ESSER cliff (Sept 2024): Federal pandemic relief expired. Districts with ESSER-funded counselors face layoffs unless they find sustainable replacement revenue. CYBHI billing is that replacement -- if they have the tools
  • LCAP Priorities 5 & 6: Every district must fund Pupil Engagement (attendance) and School Climate (mental health). A unified platform maps to both required spending categories
  • Competitive gap: No platform combines ADA recovery with mental health billing. ECS/AARC do AR manually. TadHealth does MH billing only. The connecting tissue -- a shared student record triggering both revenue streams -- does not exist
  • Per-district math: Mid-size district (20K enrolled, 19% CA): ADA recovery = $1.52M/year, CYBHI billing = $1.0M/year. Combined: $2.52M recoverable. Platform cost: $6K-$35K/year. ROI: 40-400x
  • Entry wedge: ~250 medium CA districts (2,500-10,000 students) with budget authority and faster procurement cycles than large districts

No platform in either the attendance recovery market or the mental health billing market has crossed into the other. The connecting tissue -- a shared student record that triggers both revenue streams -- does not exist.

Open Questions

Decisions That Shape Phase 3

These questions must be answered by real pilot data, not theory. Each one maps to a specific Phase 3 deliverable.

Architecture
Build or partner for MH billing?
TadHealth integration gets to market faster but cedes the highest-value module. Building in-house costs $105K-$230K upfront but owns the full value chain. Decision depends on Module 1 traction and AARC relationship trajectory.
Business Model
SaaS or revenue share?
SaaS ($500/district/month) is predictable and easier to sell. Revenue share (7% of incremental recovery) has higher ceiling and aligns incentives. Hybrid model (SaaS base + performance bonus) may be optimal. Needs 3-district data to model properly.
Product
Attendance-first or MH-first wedge?
Pre-flight decision: attendance-first. This architecture executes that decision. But the answer may shift based on first pilot district's existing infrastructure (if they already have counselors but no billing, MH is higher urgency).
Go-to-Market
Ideal pilot district profile?
Criteria: medium CA district (5K-15K students), >20% chronic absenteeism, existing counseling staff, no current Medi-Cal billing, budget authority willing to try new vendor. AARC's existing 17 districts are the first pool to evaluate.
Risk
How do we navigate inBloom comparison?
inBloom was centralized, state-run, and opaque. A winning narrative: local-first architecture, district-owned data, transparent privacy practices, opt-in only. But messaging must be proactive, not reactive to privacy advocates.
Validation
Per-district recovery yield?
The $80/day x 5 recovered days x CA students math is modeled, not validated. AARC has real district data across 17 districts. Phase 1 pilot must capture actual recovery yield to validate unit economics and finalize the business model.

Executive Read

The winning ICP is infrastructure resale with performance promises.

Latitude should not chase generic cloud migration. The strongest buyers are companies whose product is a compute abstraction for someone else: serverless AI platforms, CI/CD runners, cloud development environments, managed data systems, game-server orchestration, security scanning, real-time media, and edge compute layers. They already sell speed, isolation, locality, or predictable cost. Bare metal improves the unit economics and the SLA behind those promises.

1. Bare metal is not nostalgia.

It is the removal of abstraction where abstraction has become the bottleneck. Cloud VMs are brilliant for elasticity and procurement speed, but they still virtualize CPU scheduling, memory topology, disk, network, and often accelerator access. When a platform is at scale, the useful question is not “can the workload run on EC2?” It can. The question is “how much product margin and p99 performance is being donated to the hypervisor, shared storage, egress model, and noisy fabric?”

2. Megaport changes the story.

Plain bare metal can sound like a cheaper server. Latitude plus Megaport becomes a private compute layer: dedicated CPU/GPU/NVMe nodes connected through private VXCs, MCR, cloud on-ramps, internet exchange, and service-provider reach. The customer can keep S3, Azure Blob, BigQuery, GitHub, package registries, or enterprise data where it is while moving hot execution onto dedicated silicon.

3. Modal and Blacksmith are archetypes.

That is the ICP filter: if the target’s own value proposition includes performance, concurrency, isolation, low latency, cache locality, GPU availability, or cost transparency, Latitude has a strategic conversation instead of a commodity hosting conversation.

Section 1

Why bare metal beats cloud VMs: the deep technical truth.

A hypervisor is not a logo on an architecture diagram. It is an active software and hardware mediation layer between the workload and the machine. For general apps, that trade is often worth it. For high-throughput AI, CI, data, security scanning, and real-time platforms, the hidden tax shows up in p99 latency, GPU utilization, cache misses, I/O variance, and unit cost.

The shorthand Willie should use

VMs optimize for fleet abstraction. They let AWS, Azure, and Google carve huge machines into many rentable shapes. The provider gets high utilization and control. The customer gets elasticity and managed primitives.

Bare metal optimizes for workload truth. The customer sees the real topology: sockets, cores, NUMA domains, PCIe lanes, NVMe devices, NIC queues, interrupts, kernel, and GPU links. That visibility is not academic. It is exactly where performance engineers recover the last 10-30% of a system.

Hypervisor Tax: the 5-15% that never reaches customer code

A cloud VM is a guest operating system running on a virtual machine monitor. AWS Nitro, Azure Hyper-V, and Google’s KVM-based stack all exist to virtualize hardware: the CPU becomes vCPU, physical RAM becomes guest memory, disk becomes a virtual block device, and the NIC becomes a virtual network interface. The hypervisor schedules those virtual resources onto real silicon and enforces isolation between tenants.

That work has a cost. Modern virtualization is far better than the old emulation era, but “near native” is not “native.” The overhead depends on the workload: CPU-bound code may lose only a few percent on a well-tuned KVM/Nitro path, while interrupt-heavy networking, storage-heavy builds, and mixed CPU/GPU workloads can lose materially more. A defensible field range is 5-15% of raw CPU efficiency for many real production mixes, with occasional higher penalties when I/O and scheduling contention dominate.

The easiest analogy: a hypervisor is a brilliant hotel front desk. It allocates rooms, keeps guests isolated, routes requests, handles locks, and keeps the building full. But if you are building a factory, you may not want every forklift, delivery, door key, and power switch mediated by the front desk. Bare metal gives the platform the factory floor.

Memory is part of the same tax. Providers reserve host memory for their virtualization layer, device emulation, metadata, and management plane. Guest-visible memory is the instance shape, not the entire physical machine. On some large VMs the customer sees a clean number like 256 GiB, but host overhead and page management still sit outside the guest. On bare metal, the operating system sees and controls the whole installed memory footprint, and the performance engineer can use huge pages, lock memory, tune allocators, and place pages deliberately.

I/O is where the abstraction becomes expensive quickly. Every disk read, disk write, network packet, interrupt, and DMA mapping moves through a virtual device layer or hardware-assisted virtualization path. A few microseconds per operation sounds harmless until a CI fleet performs millions of tiny file operations, an inference service launches thousands of kernels per second, or a data platform fans out object reads across hundreds of shards. Microseconds compound into p99 tails.

Noisy Neighbor: shared hardware means borrowed variance

Cloud VMs share physical hosts, host-level network paths, storage systems, and management planes. The provider’s isolation mechanisms are good enough for most applications. They are not a guarantee that another tenant’s burst, the host scheduler, a hot NIC queue, or a storage service event will never touch your latency distribution.

CPU steal is the visible clue. In Linux, the %st column in top is time when the guest wanted CPU but the hypervisor did not let it run because the physical CPU was doing something else. Datadog’s explanation is blunt: from the app’s point of view, stolen CPU cycles are cycles the app could have used. On busy or oversubscribed hosts, teams have reported steal spikes that materially hurt throughput. The exact rate varies by instance type, provider, region, and neighbor mix, so Willie should avoid pretending every EC2 instance sees 20% steal. The defensible claim is better: any steal above low single digits is unplanned latency and capacity loss, and bare metal takes that class of risk to zero because there is no co-tenant scheduler.

Network jitter follows the same pattern. Shared NICs, virtual switches, host interrupts, noisy placement groups, and provider network fabric events can all widen p99 and p999 latency. For AI inference, tail latency is the SLA. A median of 45 ms with a p99 of 240 ms can be worse than a median of 55 ms with a p99 of 80 ms, because users and upstream services experience the tail. Bare metal gives the platform direct control over NIC queues, IRQ affinity, congestion control, and packet processing. The result is not magic latency everywhere; it is lower variance and fewer hidden schedulers in the path.

This is why the “dedicated instance” objection is incomplete. Dedicated tenancy can reduce same-host tenant competition, but it does not remove every shared component. The instance can still rely on shared provider storage, shared region network paths, managed control planes, and provider-defined host settings. Latitude’s strongest answer is single-tenant hardware plus a private fabric strategy: fewer shared layers in compute, and fewer unpredictable public-internet paths in network.

NUMA and Memory Locality: topology is performance

Modern AMD EPYC systems are not just “a lot of cores.” They are topology. NUMA means Non-Uniform Memory Access: memory access speed depends on where the memory physically sits relative to the CPU core doing the work. Local memory is attached to the same socket or NUMA domain. Remote memory crosses interconnects and costs more latency and less bandwidth.

The practical difference can be large. AMD’s NUMA material explains the basic rule: local memory has lower latency than memory attached to another NUMA domain. Independent EPYC testing shows tens of nanoseconds of penalty when memory locality is blurred, and multi-socket systems can show much larger gaps. That sounds tiny only if the workload touches memory once. Data systems, model serving runtimes, feature stores, vector indexes, build tools, compression, and packet processing touch memory constantly. Remote memory turns into lost QPS and wider p99.

Hypervisors often abstract or reshape NUMA topology so a VM sees a simplified machine. That is convenient for portability. It is bad when the application could have done better with the truth. If a scheduler places a CPU-heavy process on one socket while its memory pages live mostly on another, the code still runs, but it quietly pays the remote-memory toll. Worse, the application may not know why performance fluctuates.

Bare metal lets operators pin processes, containers, and interrupt handlers to specific NUMA nodes. They can bind memory allocation with numactl, configure Kubernetes topology manager policies, align GPU workers with the CPU socket closest to the relevant PCIe root complex, and keep hot buffers near the threads that use them. For GPU workloads this matters because CPU↔GPU data transfer, preprocessing, tokenization, networking, and storage reads often bottleneck the accelerator. The GPU is only “fast” if the rest of the machine feeds it predictably.

PCIe Passthrough and GPU Performance: accelerators hate abstraction

GPU workloads are full of small coordination events: CUDA kernel launches, memory copies, synchronization points, NCCL communication, queue management, and host-side preprocessing. Every layer that adds latency or jitter around those events hurts utilization. A GPU at 62% utilization is not a cheaper GPU; it is expensive silicon waiting for the rest of the stack.

Cloud GPU instances can expose accelerators through different mechanisms, including full-device assignment, SR-IOV, vGPU, or provider-specific virtualization. Hardware-assisted paths can be excellent, and NVIDIA documents SR-IOV as a way for packets to bypass hypervisor CPU/kernel processing in accelerated network designs. Supermicro’s GPU passthrough explainer captures the core advantage: direct assignment bypasses much of the hypervisor abstraction and can deliver near-native performance. That is exactly the point. The closer the workload gets to direct hardware, the less value the VM abstraction adds.

Latitude’s bare-metal pitch should avoid an overbroad claim that every hyperscaler GPU is “vGPU and slow.” High-end cloud GPU nodes are often very capable. The defensible claim is that Latitude gives the customer the full machine, full device topology, and full software control. There is no cloud provider host kernel between the customer and PCIe device policy. There is no need to accept provider choices about guest shape, MIG policy, kernel version, driver cadence, huge pages, or NIC/GPU affinity.

For inference, that control can improve GPU utilization and tail latency: fewer scheduling surprises, tighter CPU pinning, explicit batching, direct disk/cache paths, and topology-aware worker placement. A realistic target is 10-20% better effective utilization for mature teams that can tune the stack. For training, the same control helps gradient synchronization: NCCL, NVLink/NVSwitch topology, PCIe locality, and network interrupt affinity can be tuned together rather than inferred through a VM boundary.

Kernel and Network Stack Control: DPDK, XDP, eBPF, huge pages

On bare metal, the customer owns the kernel. That sounds mundane until the customer cares about packets, memory pages, interrupts, or latency. They can enable 2 MiB or 1 GiB huge pages, tune sysctl, choose a low-latency kernel, isolate CPU cores, bind NIC queues to cores, adjust congestion control, and run specialized packet processing stacks.

DPDK is the clearest example. The Data Plane Development Kit bypasses much of the Linux kernel network stack and lets user-space applications poll NIC queues directly with zero-copy techniques. In conventional networking, packets pass through kernel layers, interrupt handling, context switches, socket buffers, and scheduler decisions before the application acts. DPDK trades general-purpose convenience for low latency and high packet rate. In low-latency systems, reducing a network path from tens of microseconds toward single-digit microseconds can be the whole product.

Cloud VMs may offer enhanced networking, SR-IOV, and high bandwidth, but standard VMs do not let the customer reprogram the physical NIC or host kernel. XDP and eBPF at the NIC/driver layer are similar. They are powerful because they move decisions closer to the packet. On a VM, the customer is usually limited to the guest-visible interface and whatever provider abstractions are exposed. On bare metal, the platform can run packet filters, load balancers, telemetry, and custom routing closer to the wire.

Megaport extends this advantage. A tuned network stack on a Latitude server is valuable. A tuned network stack attached to private cloud on-ramps, MCR routing, and predictable VXC paths is a differentiated architecture. For regulated AI platforms, CI systems pulling private packages, and data platforms joining cloud object stores, the point is not only lower latency. It is fewer public internet paths, cleaner controls, better auditability, and stronger p99 behavior.

Storage Performance: local NVMe beats remote block for hot paths

Hyperscaler block storage is convenient because it is durable, resizable, replicated, snapshot-friendly, and separately managed from compute. That convenience is exactly why it is slower and more variable than local NVMe. AWS io2 Block Express is very good by cloud-block standards: AWS documents up to 256,000 IOPS, 4,000 MB/s, and average latency under 500 microseconds for 16 KiB operations on Nitro. That is impressive for network-attached storage. It is still not the same as local SSD sitting directly on the PCIe bus.

Local NVMe routinely reaches very high random IOPS with latency around the low hundreds of microseconds or better under tuned conditions, and there is no separate storage network hop. For CI/CD, this is decisive. A large build is not one big read. It is thousands or millions of small file stats, opens, cache lookups, decompressions, layer reads, package installs, and compiler writes. Remote cache and object storage add round trips. Local NVMe turns cache hits into disk hits inside the same machine.

Blacksmith is the clean story. Its public site says jobs run on bare-metal gaming CPUs, cache downloads are 4x faster, and Docker builds can be 40x faster because Docker layers persist on NVMe across runs. Their docs report 2x to 40x improvements from Docker layer caching. That is not a generic “bare metal is faster” claim; it is the exact mechanism: keep hot build state local and persistent where the runner executes.

For AI platforms, local NVMe matters too. Model weights, tokenizer files, compiled kernels, embedding indexes, datasets, and batch spill files all punish remote storage. The fastest H100 cluster can still idle if it repeatedly pulls weights from object storage or churns through network block volumes. Latitude’s value is to pair GPU/CPU with local disks and let the platform decide what stays hot.

Predictable Cost: platform companies need margin, not just discounts

At platform scale, infrastructure cost is not an engineering footnote. It is cost of goods sold. If Modal serves more customer workloads per GPU, its gross margin improves. If Blacksmith runs the same build minutes with fewer servers, it can price aggressively without starving the business. If an edge platform avoids egress spikes, it can offer simple pricing instead of passing cloud surprises to customers.

The current H100 pricing story requires nuance. The original brief cites AWS p5.48xlarge at roughly $98/hr for 8 H100s, or about $861K per year at 24x7 use. Current public pricing aggregators show AWS p5.48xlarge closer to $55.04/hr in us-east, while Azure ND96isr H100 and GCP a3-highgpu-8g aggregators still show roughly $98/hr and $88/hr respectively. Latitude public and aggregator pricing has also moved: the brief’s conservative $3.37/GPU-hour implies $26.96/hr for 8 H100s, while current public starting prices can appear lower depending on region, PCIe/SXM shape, and availability.

The defensible move in front of a customer is to model three cases: current list, committed cloud discount, and committed Latitude. Even with the lower current AWS comparison, $26.96/hr versus $55.04/hr is about 51% lower before storage and egress. Against the older or Azure/GCP high-$80s to high-$90s comparisons, the savings land near the brief’s 70%+ claim. Latitude’s December 2025 changelog also says yearly reserved GPU pricing can receive 50% off hourly rates, which makes committed platform economics even more compelling.

Egress is the hidden tax. AWS’s own EC2 pricing page notes data transfer out charges after the free allowance, and market references commonly cite $0.09/GB for the first 10 TB tier. Latitude’s networking page says servers include 20 TB outbound monthly and lists much lower overage bands in many regions. More importantly, Megaport private connectivity changes the architecture: move hot execution out of public cloud, keep data relationships private, and stop treating public internet egress as an unavoidable platform tax.

Section 2

The architecture: how it actually works.

The combined Latitude + Megaport architecture is not a rip-and-replace of AWS, Azure, or GCP. It is a private execution layer for the hot path. Keep object stores, customer VPCs, enterprise identity, observability, and repositories where they already live. Move the compute that needs deterministic performance onto dedicated silicon and attach it privately.

Modal pattern: serverless AI on dedicated GPU metal

Modal’s customers submit workloads through Modal’s API and SDK. Modal’s scheduler decides where to run those functions, containers, batch jobs, or inference endpoints. In the Latitude architecture, the scheduler provisions containers onto bare-metal GPU servers rather than treating cloud GPU VMs as the only substrate.

The H100/A100/L40S machines expose the real topology: GPUs connected through PCIe/NVLink/NVSwitch paths, local NVMe for model/cache/data staging, and CPU NUMA domains that can be pinned to preprocessing workers. Modal can run its own container runtime, batching strategy, model cache policy, kernel, huge pages, and network settings. The platform gets the determinism of owned infrastructure without building every data center relationship itself.

When a Modal customer needs data from S3, Azure Blob, BigQuery, Snowflake, or a private enterprise network, traffic should not hairpin over the public internet. Megaport provides the private fabric. A VXC or MCR path connects the Latitude facility to cloud on-ramps or customer networks. That path reduces public internet exposure, improves latency predictability, and supports compliance narratives around private data movement.

The result is global inference with local bare metal: US, EU, LATAM, and APAC GPU pools close to end users, with private paths back to whatever cloud still holds the customer’s data. Modal keeps its serverless developer experience. Latitude disappears under the product as the performance substrate.

Blacksmith pattern: CI/CD runners with local state

A developer pushes code to GitHub. The GitHub Actions event triggers a workflow, but instead of running on GitHub’s default hosted runner, the job routes to a Blacksmith runner. The runner is a Latitude bare-metal server with high single-core CPU performance and local NVMe. That matters because CI is a file-system workload disguised as a compute workload.

The runner pulls dependencies, checks out source, restores caches, builds Docker layers, compiles code, runs tests, and uploads artifacts. In a generic cloud runner, much of that state is remote, temporary, or expensive to persist. In the Latitude pattern, build artifacts and Docker layers stay on local NVMe across runs. The warm path is local disk rather than remote object storage. That is why Blacksmith can credibly market faster cache downloads and dramatically faster Docker builds.

Megaport strengthens the runner model in two ways. First, it can provide reliable, private, low-latency paths to package mirrors, enterprise artifact stores, and cloud registries where a customer’s dependencies live. Second, it gives Blacksmith a clearer security story: source code, packages, artifacts, and logs can move through private fabric and controlled internet services rather than relying on best-effort public paths for every dependency pull.

The strategic idea is not “replace GitHub.” It is “keep GitHub as the control plane and replace the slow execution substrate.” That same pattern applies to Depot, Namespace, Gitpod, Coder, and any platform whose users judge the product by wait time.

What performance means in business terms

For Modal: a 10-20% effective GPU utilization improvement means the same fleet can serve more customer jobs before the next capacity purchase. If 100 H100s cost roughly $2.96M/year at the conservative Latitude model, a 15% utilization gain is economically similar to finding 15 extra H100s without buying them. That can translate into faster customer onboarding, fewer queueing events, and better gross margin on usage-based compute.

For Blacksmith: 2-4x faster CI is not only developer happiness. If 200 engineers wait 20 minutes less per day, that is roughly 66 engineering hours/day recovered. At $125/hour fully loaded, that is more than $2M/year of avoided waiting. The customer may not buy on that exact spreadsheet, but it frames why CI speed is budget-worthy.

For any platform company: predictable substrate cost makes pricing easier. If the provider knows the cost of an inference minute, build minute, workspace hour, query slot, or game-session vCPU, it can package the product confidently. If the substrate is a pile of variable cloud VMs, storage IOPS, cross-AZ charges, NAT, and egress, pricing becomes defensive.

The Megaport multiplier: private connectivity adds security, compliance, deterministic latency, and multi-cloud access on top of compute savings. That lets the SA team sell an architecture, not a cheaper SKU.

Section 5

What Megaport’s SA team needs to build.

The GTM motion should make the architecture easy to believe and easy to test. A platform company will not move because a deck says bare metal is faster. It will move when the SA team shows a reference pattern, reproducible benchmark, Terraform path, and security story that maps to the customer’s product metric.

Reference architectures

Build two flagship templates: AI platform and CI/CD platform. Each should include a topology diagram, server bill of materials, VXC/MCR layout, cloud on-ramp targets, security controls, telemetry, and operational runbook. For AI, show model cache, object-store ingress, private cloud data, and multi-region inference. For CI, show GitHub trigger, runner pool, NVMe cache, package registries, artifact path, and customer network isolation.

Terraform modules

Create modules that provision Latitude servers, SSH/user-data, RAID/local disk layout, private network settings, Megaport VXC/MCR components, cloud on-ramps, firewall policy, and labels for cost attribution. The module should make the combined product feel like one platform rather than two portals stitched together by a heroic SA.

Benchmarks with scripts

Publish reproducible tests, not slides. Include vLLM inference, fio NVMe vs EBS, Docker layer restore, package install, kernel compile, NCCL multi-GPU smoke, qperf latency, iperf3 throughput, and p99 API latency. Each benchmark should include scripts, instance/server specs, region, pricing assumption, and a “how to challenge this result” note. That builds credibility with technical buyers.

Security architecture

Document how private connectivity reduces attack surface: no public ingress for management, private cloud data paths, private artifact pulls, scoped firewall rules, customer-controlled keys, logging, SOC 2 evidence collection, and incident response boundaries. Regulated buyers need the words “private” and “dedicated” translated into controls auditors can inspect.

SA qualification question: “Which product metric gets worse when your compute substrate is noisy, remote, or expensive: token latency, build time, query latency, cache hit cost, game session jitter, scan time, or gross margin?” If they can answer that, Latitude has a wedge.
